# Анализ CPU-бинарника Bloodborne и начало статической рекомпиляции

Дата анализа: 2026-10-09. Целевые платформы: Linux x86-64 и Linux ARM64 (AArch64).
Этот этап дал воспроизводимый анализ и AOT-прототип отдельных функций.
Полная рекомпиляция игры и ARM64-лаунчер пока не реализованы.

## Основной результат

Существующий `bbport` уже выполняет оригинальный процессорный код напрямую на
x86-64: `src/probe.c` отображает образ игры и вызывает его entry point, а
`src/runtime_*.c` подменяют системные API PS4. Для этого варианта CPU-рекомпиляция
не обязательна. Для отдельной сборки ARM64 нужен перевод всех исполняемых
участков игры и используемых PS4-библиотек с сохранением их поведения.

Создан конвейер `recompiler/`: plaintext SELF → проверенный ELF → диапазоны
unwind и граф переходов → выбранные целочисленные функции → LLVM IR → нативные
объекты x86-64 и AArch64. На стадии исполнения этих AOT-функций нет декодера
инструкций, интерпретатора или JIT. QEMU используется только в тестах ARM64.

## Какой именно бинарник разобран

- Источник: `game_files/CUSA03173/eboot.bin`.
- Издание: `CUSA03173`, APP_VER `01.09`.
- SHA-256 исходного SELF: `d65f0b4f01d59166aed16f8604196d8b7dd805abbf0758b356e8f1354c9429f9`.
- SHA-256 загружаемого образа: `071df19c8880086d97182dbc057bc8cb37badaca57d9112683836b24a0444c0a`.
- Размер файла: 93 825 704 байт; образа: 91 042 036 байт.
- ELF64 little-endian, x86-64, тип `0xfe10`, FreeBSD OSABI.
- Entry point: `0xa0`; обычных ELF section headers нет.
- Читается plaintext SELF; дешифрование не выполнялось.

Хеш образа совпадает с поддерживаемым 1.09 в `scripts/game_check.py`.
Исходные файлы игры читаются; все извлечённые образы и рекомпилированный код
записываются в `out/recompiler/`.

и указателей на функции.

## Обход инструкций и переходов

Zydis декодирует инструкции от известных входов. Условные переходы обходятся
по обеим веткам внутри диапазона. Прямые вызовы регистрируются как рёбра;
косвенные вызовы не раскрываются; косвенный jump завершает текущую ветку.
Поиск отдельных байтов `E8`/`E9` не используется.

Дополнительно разобраны 606 входов прямых вызовов без FDE,
в том числе 604 импортных PLT-thunks. Их RIP-relative
слоты сопоставлены с реальными релокациями и полными идентификаторами импортов.
Учтены `exit`, `abort`, `__stack_chk_fail`, которые не возвращаются.
Первый проход ошибочно заходил в inline-таблицы после этих вызовов: после
исправления число недекодируемых адресов сократилось с 843 до 22.

Финальные числа ниже относятся к обходу FDE, без добавления PLT-прохода:

восстановления графа, а не доказательство повреждения игры.

## Проверенный AOT-прототип

Из 26 651 предварительных кандидатов строгий
lifter принял 9 613. В тестовый корпус выбраны 140
функций с различными последовательностями инструкций.

Контракт ограничен: шесть сырых целочисленных входов из RDI/RSI/RDX/RCX/R8/R9,
определённый результат в RAX, без обращений к памяти, вызовов и ветвлений.
Допускается проверенная пара frame prologue/epilogue. Реализованы целочисленные
операции, частичные регистры, zero/sign extension, маскирование shift count,
LEA от входных регистров, CMP/TEST, SETcc/CMOVcc и необходимые flags.
Неопределённые входы, неподдержанная семантика и неизвестные flags отклоняются.
Имена и сигнатуры исходных функций не восстанавливались и не угадывались.

| Проверка | Результат |
|---|---|
| Оригинальные x86-64 байты против AOT x86-64 | 308 420 сравнений; 0 расхождений |
| AOT AArch64 против результатов оригинального x86-64 | 46 340 сравнений; 0 расхождений в QEMU; физический ARM не проверялся |
| Формат объектов | ELF64 x86-64 / ELF64 AArch64 |
| Неопределённые символы в AOT-объектах | 0 |

Векторы включают граничные значения 8/16/32/64-битных целых, shift counts,
нулевые входы и случайные 64-битные аргументы; seed `0xbb109`.
Сравнивался RAX; полный набор регистров, состояние FP и ABI всей игры не проверены.
ARM64-тест — freestanding Linux ELF без libc и динамического интерпретатора.
На физическом ARM-процессоре проверки не проводились.

Артефакты: `leaves.ll`, `leaves-x86_64.o`, `leaves-aarch64.o`,
`leaves-x86_64.so`, `arm-check`, `lift.json`, `verification.json`, дизассемблирование
обоих объектов. Они содержат производный код из локального дампа и остаются в `out/`.

## Что нужно для двух вариантов запуска всей игры

1. Завершить восстановление CFG: устранить 22 decode failures,
   3 конфликта, 5 635 выходов
   за границу диапазонов; раскрыть switch tables, callbacks и exception landing pads.
   Собрать тесты для новых типов функций на оригинальном x86-64.
2. Добавить полный lifter для памяти, стеков, ветвлений, SSE/AVX/BMI и FP.
   Сохранить x86 flags, MXCSR/FP rounding, NaN-поведение, порядок памяти и LOCK.
   На ARM нельзя заменить x86 атомарные операции и TSO обычными C-записями.
3. Ввести согласованное отображение guest адресов кода в AOT entry points.
   Прямые вызовы, vtable, сохранённые callbacks, создание потоков и обратные вызовы
   рантайма должны использовать одну модель. Адреса данных и layout PS4 сохраняются.
4. Перевести или заменить используемые PS4 PRX. `bbport` сейчас прилинковывает
   `libc.prx` и `libSceFios2.prx` как оригинальный x86-код; они также нужны на ARM:

   | Модуль | RX-байты | FDE | Импорты |
   |---|---:|---:|---:|
   | libc.prx | 751 908 | 2 164 | 79 |
   | libSceFios2.prx | 309 956 | 650 | 83 |

5. Перенести архитектурные части рантайма: запрет ARM в `src/probe.c`, x86 asm
   входа/импортных trampoline, FS→GS/`arch_prctl` в `runtime_thread.c`, обработчики
   `REG_RIP`/`ucontext`, guest `setjmp`/unwind и SysV→AAPCS64-мосты.
   Проверить архитектурные зависимости GPU-ядра: SIMD headers, trap handlers,
   Xbyak в `flatten_extended_userdata_pass.cpp`: его не-x86 ветка сейчас вызывает
   `UNREACHABLE_MSG` и не реализует проход. Vulkan-рендерер остаётся необходимым.
6. Получить отдельный ARM64 executable и пройти последовательные smoke-проверки:
   entry → initialization → title screen → loading save → gameplay/audio/saving.
   После этого добавлять выбор CPU-архитектуры и упаковку двух сборок.

Прототип подтверждает практический перевод конкретных функций в обе ISA.
Он не подтверждает, что вся игра уже переносится автоматически или будет иметь
ту же производительность. x86-64 direct execution можно сохранять как рабочий
вариант и как эталон для проверки ARM64-рекомпиляции.

## Воспроизведение

Из `bbport/`:

```bash
nix-shell recompiler/shell.nix --run 'bash recompiler/run.sh ../game_files/CUSA03173'
```

Нужны GCC, CMake, Ninja, Python 3, Zydis 4, LLVM 21, LLD и QEMU user-mode.
Текущий прогон: GCC 15.3, Zydis 4.1.1, LLVM 21.1.8, LLD 22.0 (ROCm), QEMU 11.1.1.
Также можно запускать `bash recompiler/run.sh GAME_DIR` в готовом окружении.
`BB_RECOMP_OUT` задаёт каталог артефактов; `BB_LLVM_BIN`, `BB_LLD`,
`BB_QEMU_AARCH64` позволяют выбрать установленные инструменты.
Конвейер проверяет хеш исходного бинарника и не запускает игру.

## Источники для следующего этапа

Для расширения lifter рассмотрен [Remill](https://github.com/lifting-bits/remill):
это библиотека семантики машинных инструкций и подъёма в LLVM IR, включая amd64.
Она не решает автоматически PS4 runtime/CFG и не встроена в текущий прототип.
[Ограничения McSema](https://github.com/lifting-bits/mcsema/blob/master/docs/Limitations.md)
отдельно описывают code/data recovery, self-modifying code и исключения;
рассматривать этот инструмент как готовый конвертер всей игры нельзя.

Мост вызовов ARM должен соответствовать
[AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst);
перенос исключений требует отдельного разбора
[C++ Exception Handling ABI](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html).
Все численные результаты выше получены локальными инструментами из указанного SELF.
